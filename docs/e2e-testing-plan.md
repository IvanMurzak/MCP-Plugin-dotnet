# План тестирования интеграции MCP-сервера с AI-агентами (Cross-Platform)

## Цели тестирования
1. **Проверка подключения:** Убедиться, что различные AI-агенты (Antigravity, CloudCode и др.) могут успешно настроиться и подключиться к MCP-серверу.
2. **Кроссплатформенность:** Гарантировать корректную работу на Windows, macOS и Linux (с учетом специфичных для ОС багов конфигурации путей, переносов строк и `stdio`).
3. **Режимы подключения:** Тестирование как `stdio` (агент сам запускает процесс), так и `sse` / HTTP (подключение к заранее запущенному серверу с выделением портов).
4. **Изоляция:** Среда должна быть "чистой" для загрузки свежей версии агента, генерации конфигов и во избежание конфликтов портов.

---

## Архитектура решения

Поскольку нам нужно тестировать **macOS и Windows-специфичные баги** (например, баг конфигурации Antigravity), использование **только Docker не подойдет**, так как Docker на macOS и Windows по умолчанию запускает Linux-контейнеры. (Windows-контейнеры существуют, но они тяжеловесны, а macOS-контейнеров в Docker нет).

Поэтому мы будем комбинировать **GitHub Actions (как эталонную изолированную среду)** и **Локальные песочницы** для разработки.

### 1. Компонент "Пустышка" (Dummy MCP Server)
Необходимо создать минималистичный MCP-сервер (например, C# Console App в рамках этого же репозитория, `McpPlugin.DummyServer`).
*   **Функционал:** Поддерживает аргументы `--transport stdio` и `--transport sse --port <PORT>`.
*   **Инструменты:** Регистрирует один инструмент `ping` (возвращает `pong`).
*   **Телеметрия:** Пишет логи в файл (например, `dummy_server.log`), чтобы тестовый раннер мог прочитать этот файл и убедиться: "Да, агент Antigravity успешно вызвал tool ping".

### 2. Тестовый Оркестратор (Test Harness)
Скрипт или проект (например, на Python, Node.js или C# xUnit/NUnit с использованием `Process`), который управляет всем процессом:
1.  **Setup:** Создает временную директорию (temp dir). Устанавливает туда или скачивает свежую версию AI-агента (Antigravity CLI / VS Code с CloudCode).
2.  **Config Generation:** Генерирует конфигурационный файл для агента (например, `config.json`), подставляя правильные абсолютные пути к Dummy MCP Server (важно для проверки слэшей `\` vs `/`).
3.  **Run Server (for SSE):** Если тест HTTP, поднимает Dummy Server на свободном порту.
4.  **Execute Agent:** Запускает AI-агента в headless-режиме и отправляет ему промпт типа "Вызови инструмент ping".
5.  **Assert:** Проверяет stdout агента и логи Dummy-сервера на успешность.
6.  **Teardown:** Убивает процессы, удаляет временную директорию.

### 3. Среды выполнения (Изоляция)

#### Вариант А: Идеальная изоляция через CI/CD (GitHub Actions)
GitHub Actions предоставляет свежие виртуальные машины для каждого запуска. Это **идеальная изолированная среда**, которая решает проблемы с портами и гарантирует чистую установку.
```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest, macos-latest]
    agent: [antigravity, cloudcode]
    transport: [stdio, sse]
```
В каждом джобе скачивается нужный агент, генерируется конфиг и прогоняется оркестратор.

#### Вариант Б: Локальная изоляция (Для локального дебага)
Разработчикам нужно иметь возможность запустить тесты локально перед пушем.
*   **Linux:** Docker-контейнер. Скрипт поднимает контейнер, монтирует Dummy Server, ставит агента, прогоняет тест.
*   **Windows:** Использование Windows Sandbox (встроенная легковесная виртуалка) или просто запуск тестов во временной папке (temp directory isolation), так как полная виртуалка для каждого теста локально будет слишком медленной.
*   **macOS:** Запуск во временной папке. Изоляция достигается за счет того, что оркестратор использует уникальные пути для конфигов (например, переопределяя `$HOME` или специфичные переменные среды, чтобы агент не читал глобальные конфиги юзера).

## План реализации (Пошаговый)

**Шаг 1: Создание Dummy MCP Server**
*   Добавить проект `McpPlugin.DummyServer`.
*   Реализовать поддержку `stdio` и `sse`.
*   Добавить логирование в файл для удобства проверок.

**Шаг 2: Написание E2E Test Runner'а**
*   Выбрать технологию для оркестратора (предлагаю C# xUnit или Python скрипты для простоты работы с ОС процессами).
*   Написать адаптер для установки и запуска **Antigravity** (так как это текущая боль).
    *   *Пример:* Скрипт делает `npm install -g @google/antigravity` (или аналог), подкладывает конфиг с `stdio` на наш DummyServer.
*   Написать адаптер для **CloudCode**. (Здесь будет сложнее, так как это расширение для IDE. Потребуется использовать `@vscode/test-cli` для запуска VS Code в headless режиме с расширением CloudCode).

**Шаг 3: Тесты для Antigravity**
*   Написать тест: "Antigravity подключается по `stdio`".
*   Написать тест: "Antigravity подключается по `sse`".

**Шаг 4: Настройка CI/CD (GitHub Actions)**
*   Добавить воркфлоу `e2e-agents-test.yml`.
*   Настроить матрицу (Windows, Mac, Linux).
*   Убедиться, что баг с Antigravity воспроизводится на CI (тест падает), затем исправить баг конфигурации в самом Antigravity или плагине (где он на самом деле находится) и увидеть зеленый тест.

---
## Резюме по поводу Docker
Для задачи "тестировать баги путей на macOS и Windows" Docker **не подходит** как единственный инструмент. Он отлично изолирует Linux, но скроет баги Windows/macOS. Поэтому лучшая стратегия: **Изоляция на уровне файловой системы + процессов локально** (каждый тест в своей Temp-папке на свободном порту) и **Полная изоляция на уровне ВМ в GitHub Actions** (где OS native).
